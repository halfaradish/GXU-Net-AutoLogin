# 广西大学校园网：已核实事实与核心结论

本文记录对广西大学校园网（认证门户、会话状态、网络特征）的实测结论，与任何客户端程序无关。
每条结论都标注了证据来源，未经验证的一律标为 `推断`，不做结论使用。

**证据标注**

| 标注 | 含义 |
|------|------|
| `实测` | 在真实校园网环境中直接观测到的数据 |
| `对照实验` | 控制单一变量后对比服务器响应得出的结论 |
| `文档` | 学校官方文档中明确写出的内容 |
| `推断` | 由现有证据推出，尚未直接验证 |

采集时间：2026-09-20。采集点：校园网内一台 Windows 客户端，分别经 WiFi 与有线接入。
本文不含任何真实账号、密码或凭据。

## 2. 认证门户接口

### 2.1 地址与形式（`文档` `实测`）

```
GET http://172.17.0.2:801/eportal/portal/login
```

- 认证前即可访问（属于免认证放行范围），无需先联网。
- 返回 `HTTP 200`，响应体是 JSONP 包裹的 JSON：`dr1003({...});`
- 请求参数与学校官方文档给出的命令行登录方式一致：

| 参数 | 值 / 含义 |
|------|----------|
| `callback` | `dr1003`（JSONP 回调名） |
| `login_method` | `1` |
| `user_account` | 账号，需要带运营商后缀时写作 `账号@cmcc` / `@unicom` / `@telecom` |
| `user_password` | 密码（明文 GET 传参） |
| `wlan_user_ip` | 待认证终端的 IP |
| `wlan_user_mac` | 终端 MAC（无冒号小写）。官方文档示例使用 `000000000000` |
| `wlan_user_ipv6` | 空 |
| `wlan_ac_ip` / `wlan_ac_name` | 空 |
| `jsVersion` | `4.2.1` |
| `terminal_type` | `1` |
| `lang` | `zh-cn` |
| `v` | `5574` |

> 官方文档：<https://net.gxu.edu.cn/info/1360/2293.htm>（2021-02-06 更新，内容为 Linux 下的
> 命令行登录方式，含完整 curl 示例）。文档只给出登录方式，**没有错误码表**。

### 2.2 响应字段（`实测`）

响应 JSON 含三个字段：

| 字段 | 观察到的取值 | 含义 |
|------|-------------|------|
| `result` | `1` / `0` | 1 = 认证成功；0 = 未成功（具体原因看 msg） |
| `msg` | `"Portal协议认证成功！"` / `"512"` / `"账号不存在"` | 成功提示，或错误码 / 错误描述 |
| `ret_code` | 数字 `2`，或字符串 `"1"` | 伴随 msg 出现的辅助码 |

## 3. 响应语义：对照实验

在**本机已有会话（能正常上网）**的状态下，用真实账号请求登录接口，逐一改变单个变量：

| 实验 | 改变的变量 | 服务器响应 |
|------|-----------|-----------|
| A | 无（真实账号 + 正确密码 + 无关网卡的 MAC） | `result:0, msg:"512", ret_code:2`（连续 10 次全部一致） |
| B | 仅 MAC 改为该终端真实网卡 MAC | `result:0, msg:"512", ret_code:2` |
| C | 仅 MAC 改为全零（官方文档示例值） | `result:0, msg:"512", ret_code:2` |
| D | 仅账号改为不存在的 `0000000000` | `result:0, msg:"账号不存在", ret_code:"1"` |
| E | 真实账号 + **正确**密码 | `result:0, msg:"512", ret_code:2` |
| F | 真实账号 + **错误**密码 | `result:0, msg:"512", ret_code:2` |

由对照实验可得：

- **E 与 F 完全相同** → 服务器在返回 512 时**根本没有校验密码**，说明它是在认证流程
  之前就被短路拒绝，512 不是对凭据的评价。
- **A / B / C 完全相同** → 512 与 MAC 无关，服务器不校验 MAC（与官方文档示例传全零一致）。
- **D 返回明确中文错误** → 服务器确实会区分账号状态，存在独立于 512 的账号检查。

### 3.1 决定性验证：无会话时的同一请求（`实测`）

断开网络（无会话）后，用同一个账号、同一个请求再次登录：

```
dr1003({"result":1,"msg":"Portal协议认证成功！"});
```

**同一请求在有会话时返回 512、无会话时返回成功**，因此 512 的语义确定为：
**该 IP 已有会话，无需重复认证。**

### 3.2 服务器检查顺序（`推断`）

综合 D（账号不存在有专属错误）与 A/E/F（512 无视密码），最可能的顺序是：

```
账号格式/存在性检查 → 会话状态检查（已有会话则 512） → 真正的认证（校验密码）
```

一处尚未解释的观察（`实测`，待探索）：不存在的账号 `1234567890` 返回的是 512 而非
"账号不存在"，而 `0000000000` 返回"账号不存在"。推测第一关只做格式校验
（纯数字、不以 0 开头等），真正的存在性校验在更靠后的环节。

## 4. 会话与状态

| 观察 | 内容 | 证据 |
|------|------|------|
| 会话绑定 | 会话以 IP 为主键；同一 IP 有会话时所有登录请求被 512 拒绝 | `对照实验` |
| 重复认证 | 重复提交登录请求不会影响已有会话，服务器直接拒绝，不会踢下线 | `实测` |
| 认证前置 | 无会话时无法访问公网；登录成功后立即恢复 | `实测` |
| 认证身份 | 提交的 `wlan_user_ip` 决定为哪个 IP 建立会话 | `推断` |

> 由此可知：在已联网状态下反复请求登录接口是"无害但无效"的行为——服务器只会回 512。

## 5. 网络可达性与延迟特征

### 5.1 到公网端点的延迟（`实测`）

对 `http://connect.rom.miui.com/generate_204` 以 1 秒间隔连续探测，客户端与服务器共用
keep-alive 连接（省去重复的 DNS 与握手）：

| 接入方式 | 采样数 | 失败 | p50 | p90 | p99 | max |
|---------|-------|------|-----|-----|-----|-----|
| WiFi（10.1.175.x 段） | 150 | 0 | 58ms | 98ms | 142ms | **619ms** |
| 有线（172.30.129.x 段） | 120 | 0 | 49ms | 51ms | 72ms | **115ms** |

- 两种接入均未出现真实断网，但 **WiFi 下出现过 619ms 的延迟尖峰**（约为中位数的 10 倍）。
- 有线接入的延迟非常稳定（p90 仅 51ms），无线链路的抖动（重传、漫游、信号波动）
  是延迟尖峰的主要来源。
- 新建连接的开销（`实测`，冷启动）：DNS 约 7ms + TCP 握手约 90ms，首字节约 140~180ms；
  复用连接时约 50ms。

### 5.2 DNS（`实测`）

| 项 | 值 |
|----|----|
| 校园 DNS 服务器 | `210.36.18.196` |
| `connect.rom.miui.com` 解析结果 | CNAME `miphone-ai-platform-pri-prod.alb.xiaomi.com` → `39.101.90.164`、`120.133.85.84`（小米在阿里云上的负载均衡） |

### 5.3 认证前后的连通性（`实测`）

| 状态 | 公网可达性 |
|------|-----------|
| 未认证（无会话） | 公网不可达，仅门户等放行地址可访问 |
| 已认证 | 公网可达，实测 `http://www.baidu.com` 返回 200，耗时约 50~115ms |

## 8. 采集方法说明

本节描述数据是怎么得到的，便于复现（不依赖任何特定程序）。

| 方法 | 用途 |
|------|------|
| 直接 `curl` 门户接口 | 获取登录响应，逐项改变参数做对照实验 |
| 定时探测公网端点并记录耗时 | 得到延迟分布与尖峰；用长连接可分离"连接建立"与"链路"两部分开销 |
| `nslookup` / `ipconfig` | 确认 DNS 服务器、解析结果、本机地址段与网关 |
| 断开认证后重试同一请求 | 验证 512 与成功响应的分界（会话有无） |

注意事项：

- 登录接口的密码是**明文 GET 传参**，在任何抓包、日志、命令历史中都可能留存。
- 对门户接口做对照实验时，重复提交登录请求不会影响已有会话，但仍建议控制频次。
